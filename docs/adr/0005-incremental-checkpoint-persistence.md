# 增量落盘 checkpoint，而非批次结束后一次性持久化

`ingest()` 的 Phase 1（逐文件 `cognee.add()`/`update()`）曾经只在整个 for 循环跑完之后调用一次 `save_hashes()`。这是一个 bug：对大 vault（几十上百个文件）而言，Phase 1 本身可能跑很久（每文件都有一次网络/LLM 调用），中途被打断（Ctrl+C、进程被杀、崩溃）就会让所有已经成功 `cognee.add()` 的文件的进度全部丢失——`hashes.json` 里完全没有记录。下次运行会把这些文件当成全新文件重新 `add()`，在 Cognee 图谱里产生重复节点（同一份内容两个不同的 data_id）。

修复方式：每处理完一个文件，立即调用一次 `save_hashes()`，不再等整批循环结束。同时把 `save_hashes()` 改成原子写入（写临时文件 + `os.replace`），避免高频写入时进程被杀导致 JSON 文件本身被截断/损坏。

## 为什么

- **崩溃安全性优先于 I/O 效率。** 多写几次几十 KB 的 JSON 文件，代价远小于让用户重新等待/重新花 LLM 调用成本去处理本来已经成功的文件，更远小于图谱里产生重复节点这种脏数据问题。
- **checkpoint 的意义就在"能随时中断随时恢复"。** 如果只在整批结束时落盘一次，那这个 checkpoint 机制在最需要它的场景（长循环、易被打断）恰好失效——这违背了它存在的目的。

## 权衡

- **代价**：每文件多一次磁盘写入（含 fsync 语义的 `os.replace`），对几十到几百个文件量级可忽略；对未来如果文件数量级到万级，可考虑改为"每 N 个文件批量落盘一次"而非每文件必落盘，是可接受的性能/安全性折中。
- **收益**：中断后重新运行能正确识别已完成的文件，不重新处理、不产生重复数据；`hashes.json` 本身也不会因为进程被杀在写入过程中而损坏。
- **被拒绝的替代方案**：只在 Phase 1 结束时落盘一次（原实现，已证实是 bug 根因）；用内存队列 + 定时落盘（引入不必要的时间窗口和复杂度，对这个量级没有必要）。

## 通用规则（适用于本项目所有类似循环）

> 任何"逐项处理外部资源（网络调用/LLM 调用）+ 落盘 checkpoint 记录进度"的循环，必须在**每一项处理成功后立即持久化**该项的 checkpoint，不能只在整批循环结束后统一持久化一次。

配套的测试标准：

> 任何对外声称支持"可中断、重新运行可恢复/不重复处理"的功能，回归测试集里必须包含至少一个**模拟循环中途中断**（而非仅测试完整跑完/完全不跑）的用例，验证中断前已完成的部分被正确持久化、且恢复后不会被重复处理。仅测试"完整成功"和"完全失败"两种边界，不足以覆盖这类 bug。

参见 `tests/integration/test_interrupt_resilience.py`。
